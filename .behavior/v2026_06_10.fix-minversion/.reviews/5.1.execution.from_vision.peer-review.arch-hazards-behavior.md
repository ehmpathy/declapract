# blocker.1: Hidden side effect via disk I/O for package name during JSON fix

**rule**: .agent/repo=bhuild/role=behaver/briefs/practices/behavior.execution/architect/rule.forbid.behavior-hazards.md

**locations**:
- src/domain.operations/declaration/readPracticeDeclarations/readPracticeDeclaration/getFileCheckDeclaration/fixMethods/fixContainsJSONByReplacingAndAddingKeyValues.ts

fixContainsJSONByReplacingAndAddingKeyValues performs an internal file read from disk (via readFileIfExistsAsync + context.getProjectRootDirectory) to compute targetPackageName for self-dep filtering when context.relativeFilePath === 'package.json'. This is a hidden side effect not obvious from the (contents, context) signature. The 'contents' param already holds the package.json being fixed, yet disk is re-read. If on-disk state differs from provided contents (e.g. concurrent edits, TOCTOU between check and fix phases, or partial writes), filtering uses wrong name. This can silently include/exclude self-deps, produce incorrect fixes, or cause runtime issues like circular deps. Reads can also fail unpredictably (permissions, missing file) leading to null name and no filtering (unexpected default). Violates requirement for predictable behavior with no hidden side effects or race conditions.

**snippet**:
```ts
const getTargetPackageName = async (
  context: FileCheckContext,
): Promise<string | null> => {
  const projectRoot = context.getProjectRootDirectory();
  const packageJsonPath = path.join(projectRoot, 'package.json');
  const contents = await readFileIfExistsAsync({ filePath: packageJsonPath });
  if (!contents) return null;
  const parsed = parseJSON<{ name?: unknown }>(contents);
  return typeof parsed?.name === 'string' ? parsed.name : null;
};

// later in fix:
const isPackageJson = context.relativeFilePath === 'package.json';
const targetPackageName = isPackageJson
  ? await getTargetPackageName(context)
  : null;
const processedDeclaredJSON = targetPackageName
  ? processSelfDepsForFix({
      declared: declaredPackageJSON as Record<string, unknown>,
      found: foundPackageJSON as Record<string, unknown>,
      targetPackageName,
    })
  : declaredPackageJSON;
```

# blocker.2: Race condition / TOCTOU between check contents and disk read for name

**rule**: .agent/repo=bhuild/role=behaver/briefs/practices/behavior.execution/architect/rule.forbid.behavior-hazards.md

**locations**:
- src/domain.operations/declaration/readPracticeDeclarations/readPracticeDeclaration/getFileCheckDeclaration/fixMethods/fixContainsJSONByReplacingAndAddingKeyValues.ts

When fixing package.json, the function receives 'contents' (the state at check time) but re-reads the name from disk inside getTargetPackageName. This is a read-modify-write sequence without protection or consistent snapshot. If the package.json on disk changes between the initial contents read (in check phase) and the name read (in fix), or if multiple fixes run, self-dep filtering will see inconsistent state. Can cause duplicate self-deps, omitted required deps, or wrong package name used. Fits race condition and order-dependence hazards that pass tests but fail in production under load or concurrent use.

**snippet**:
```ts
if (!contents)
  return { contents: ... };

const foundPackageJSON = parseJSON(contents);
const declaredPackageJSON = parseJSON(declaredContents);

const isPackageJson = context.relativeFilePath === 'package.json';
const targetPackageName = isPackageJson
  ? await getTargetPackageName(context)
  : null;
const processedDeclaredJSON = targetPackageName
  ? processSelfDepsForFix({ declared: ..., found: ..., targetPackageName })
  : declaredPackageJSON;
const fixedPackageJSON = deepReplaceOrAddCurrentKeyValuesWithDesiredKeyValues({
  currentObject: foundPackageJSON,
  desiredObject: processedDeclaredJSON,
});
```
